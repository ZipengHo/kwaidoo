# GPF 微服务开发

## 适用范围

适用：

- TinyService 微服务接口与实现开发
- 服务路由、追踪、钩子、跨服务调用
- 微服务实战场景和常见错误排查

不适用：

- 普通 HTTP 接口开发
- 规则函数开发
- 普通 Cell 或基础 API 的局部修改

## 输入契约

至少确认以下信息：

- 服务目标、调用方与被调用方
- 服务接口、请求参数、返回结果
- 接口入参与返回值是否只依赖基础类型、基础集合或可序列化的贫血 POJO
- 是否涉及路由、追踪、钩子、超时或失败重试
- 当前服务代码、接口定义或报错现象

如果用户明确提到下列任一类，必须优先读取 `references/Ts核心类与调用示例.md`：

- `tiny.service.cmn.TsHelper`
- `tiny.service.cmn.TsOption`
- `tiny.service.cmn.TsHook`
- `tiny.service.cmn.TsProviderHook`

## 执行步骤

1. 判断任务是否以微服务为最终交付物。
2. 读取 `references/资料索引.md`，按需选择本地专题摘要。
3. 统一读取 `references/通用规范摘要.md`。
4. 如果任务涉及跨服务调用、路由、追踪或钩子，读取 `references/Ts核心类与调用示例.md`。
5. 搜索现有服务接口、实现和调用模式，优先复用当前项目服务边界。
6. 设计微服务接口与实现时，先按普通 Cell 的接口/实现分层规范组织代码，再检查接口参数和返回类型是否满足跨代理下发运行的解耦要求。
7. 生成或修改代码时明确接口契约、服务路由、异常传播和观测点。
8. 完成后检查跨服务调用失败、路由配置和追踪信息是否闭环。

## 输出契约

输出应包含：

- 微服务接口或实现方案
- 请求与返回契约说明
- 接口类型约束说明，尤其是入参与返回值是否可脱离具体代理工程独立传输和运行
- 路由、追踪、钩子或错误处理要点
- 涉及 `TsHelper/TsOption/TsHook/TsProviderHook` 时，明确说明调用入口、参数作用范围和执行侧
- 未确认的服务边界或注册前提

## 自检清单

- 是否明确服务边界和接口契约
- 是否检查接口入参与返回值没有绑死在某个微服务代理私有工程类型上
- 是否说明跨服务调用的失败模式
- 是否在需要时补齐路由、追踪和钩子处理
- 是否区分消费端 Hook 与提供端 Hook
- 是否给出 `TsHelper.openService(...)` 和 `TsOption` 的具体使用方式
- 是否避免把微服务问题错误简化成普通 HTTP 接口问题

## 强制规范

- 严禁编造工程中已存在类的包路径、接口定义、方法签名、继承关系或返回类型
- 微服务接口本质上可以按普通 Cell 接口方式设计，但接口入参与返回值必须保持跨代理解耦
- 微服务接口与实现的组织方式应遵循普通 Cell 的基础规范：先定义接口，再提供实现；不要把远程调用约束误写成随意的工具类静态调用
- 微服务接口不支持按服务 Cell 方式建模，不要引入 `ServiceCellIntf`、`BasicServiceCell` 或服务 Cell 生命周期概念
- 定义在微服务接口上的类型，优先使用基础类型、基础集合类型或可序列化的贫血 POJO；避免带运行时依赖、管理器能力、数据库句柄、Cell 上下文或复杂行为对象
- 只要微服务接口使用了非基础类型 DTO/POJO，该类型就必须明确满足序列化要求，不能只保留字段结构而缺少可序列化能力
- 微服务接口契约不得依赖某个具体微服务代理上的私有 Java 工程类型；否则无法保证接口能下发到每个微服务代理并被统一调用
- 只要输出里引用现有微服务接口、服务实现、路由器、追踪或钩子类，就必须先以当前工程源码或技能内源码快照为准完成核实
- 如果当前技能目录内还没有对应源码快照，应先根据 `references/源码类索引.md` 定位待核实类，再决定是否把最小必要源码收敛进技能目录
- 如果类名能确认但包路径、接口方法或实现细节不能确认，必须明确标注“待从源码核实”，不得补全猜测值

输入：

- “基于 TinyService 写一个查询订单详情的微服务，并说明路由和追踪要点”
- “解释 TsHelper、TsOption、TsHook、TsProviderHook 怎么配合使用，并给出调用示例”

预期：

- 输出微服务导向的实现方案
- 明确接口契约、路由与追踪
- 能区分消费端与提供端 Hook，并给出 `openService(...)` 示例
- 不混同为普通 HTTP 接口开发
